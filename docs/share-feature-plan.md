# 実装計画書: 3分診断の結果共有・保存機能

**対象サイト**: ルート大全 (https://route-taizen.com/)
**目的**: 診断結果をURLで再現・共有できるようにし、X(Twitter)等での拡散とリピート訪問を促す。あわせてlocalStorageで結果を端末に保存できるようにする。
**実装者**: Claude Code
**最終更新**: 2026-08-25
**リポジトリへの取り込み**: 2026-08-26。Phase 0 の調査結果と本計画書の差異は [`share-feature-survey.md`](share-feature-survey.md) の「9. 計画書との差異」に記録している。実装は差異の解消後の方針に従う。

---

## 0. この計画書の使い方(Claude Codeへの指示)

- Phase 0 から順に実施する。**各Phaseの受け入れ条件をすべて満たしてから次に進む**こと。
- Phase 0 の調査結果と本計画書の前提が食い違う場合は、**実装を進めず、差異と修正案を報告して停止**する。
- 新しいnpm依存・フレームワーク・ビルドツールを**追加しない**。既存の技術スタックの範囲で実装する(サイトが静的HTML+バニラJSであればその範囲で完結させる)。
- 作業はfeatureブランチ(`feature/share-diagnosis-result`)で行い、Phaseごとにコミットを分ける。
- 既存の診断ロジック・スタイル・他ページには**一切手を入れない**。触るのは診断関連ファイルと、新規追加ファイルのみ。

## 1. 設計方針(最重要・全Phaseに適用)

### 1-1. 「結果」ではなく「回答」をURLに載せる

共有URLには診断の**計算結果ではなく、ユーザーの回答(入力値)をエンコード**する。URLを開いた側は、現行の診断ロジックで結果を**再計算**して表示する。

理由:
- 結果(参考書リスト)をURLに載せると、将来ロジックや収録書籍を更新した際に「URLの中身」と「現行ロジック」が乖離し、古い・存在しない結果が表示される不具合の温床になる。
- 回答のみなら、URLは常に短く、結果は常に最新ロジックで整合する。
- 副作用として、ロジック改善が過去の共有URLにも自動反映される。

### 1-2. スキーマはバージョン管理する

- すべての共有URLに `v=1` を含める。
- 将来、質問の追加・削除・選択肢変更でスキーマが変わる場合は `v=2` を発行し、`v=1` の扱い(変換して表示 or 「診断をやり直してください」への誘導)をその時点で決める。**バージョン不明・未対応のURLは必ず診断開始画面へフォールバック**させる。

### 1-3. すべてのパラメータをホワイトリスト検証する

- URLパラメータは信頼しない。各パラメータは「定義済みの値の集合に完全一致するか」だけを検証し、一致しなければ**そのパラメータを不正として全体をフォールバック**(部分復元はしない。中途半端な状態が最も不具合を生む)。
- パラメータ値を`innerHTML`等でDOMに**直接挿入することを禁止**する。表示に使うのは、検証を通過したIDから引いた**内部定義のラベル文字列のみ**。これでXSSを構造的に防ぐ。

### 1-4. プログレッシブエンハンスメント

- JSが無効・エラー時でも既存の診断ページが壊れないこと。共有ボタン群はJS初期化成功後にのみ表示する。

## 3. Phase 1: URLスキーマの設計と実装

### 3-1. スキーマ定義

診断結果URLの形式(例。実際のパス・パラメータ名はPhase 0の調査結果に合わせて確定する):

```
https://route-taizen.com/{subject}/shindan/?v=1&a=2.1.3.4.2
```

| パラメータ | 意味 | 形式 | 検証ルール |
|---|---|---|---|
| `v` | スキーマバージョン | 正の整数 | 現在は `1` のみ許可 |
| `a` | 回答列 | 各質問の選択肢インデックス(0始まりまたは1始まり、コード内定数で統一)をドット区切り | 要素数が当該科目の質問数と完全一致、かつ各値がその質問の選択肢範囲内 |

設計ルール:
- 科目はパス(`/english/shindan/` 等)で表現されるならパラメータにしない。単一ページ診断なら `s=english` を追加し、科目IDもホワイトリスト検証する。
- 区切り文字はURLエンコード不要な文字(`.` または `-`)を使い、URL全体を人間が見ても壊れていないと分かる形にする。
- **URL全長が2,000文字を超えない**ことを設計段階で確認する(回答列方式なら質問20問でも余裕で収まるはず)。

### 3-2. 実装

新規ファイル `assets/js/share-diagnosis.js`(パスは既存構成に合わせる)に以下を実装:

1. `encodeAnswers(subjectId, answers) -> string` : 回答配列から共有URLを生成
2. `decodeAnswers(searchParams) -> {ok: true, subjectId, answers} | {ok: false, reason}` : パラメータの検証つき復元
3. 上記2関数は**純粋関数**として実装し、DOM操作を含めない(Phase 6のテスト容易性のため)
4. エンコード→デコードのラウンドトリップで元の回答配列が完全復元されることをコード内コメントで保証条件として明記

### 受け入れ条件

- [ ] 全科目・全回答パターンで encode→decode がラウンドトリップする
- [ ] 不正値(範囲外インデックス、要素数不足・過多、非数値、未知の`v`、パラメータ欠落)がすべて `{ok: false}` になる
- [ ] 純粋関数としてDOM非依存で実装されている

## 4. Phase 2: URLからの結果復元(ディープリンク)

### タスク

1. 診断ページ読み込み時に `v` と `a` の存在をチェックする処理を追加:
   - 有効 → 質問画面をスキップし、復元した回答で既存ロジックを実行して**結果画面を直接表示**。画面上部に「共有されたルートを表示しています」と小さく明示し、「自分でも診断する」ボタンを併置する。
   - 無効 → パラメータを無視して通常の診断開始画面を表示。**エラー画面は出さない**(壊れたURLを踏んだ人を診断に自然に誘導する)。控えめに「リンクの読み込みに失敗したため、最初から診断できます」と1行表示する。
2. 復元表示時、ブラウザの「戻る」で共有URLの結果に戻れること(`history` を壊さない)。
3. 復元処理は既存の結果算出関数を**そのまま呼ぶ**。復元用に結果ロジックを複製しない(二重実装は乖離バグの温床)。

### 受け入れ条件

- [ ] 有効なURLで、質問に答えることなく結果が表示される
- [ ] その結果が、同じ回答を手動入力した場合と完全に一致する
- [ ] 無効なURL(手で改変した10パターン以上で確認)がすべて通常の診断開始画面に静かにフォールバックする
- [ ] JSエラーがコンソールに出ない

## 5. Phase 3: 共有UI

### タスク

結果画面の下部(最初の参考書の提示より下、邪魔にならない位置)に共有ブロックを追加:

1. **リンクをコピー**: `navigator.clipboard.writeText()`。非対応環境では選択済みテキストボックスを表示するフォールバック。成功時は「コピーしました」を2秒表示。
2. **Xで共有**: `https://x.com/intent/post` へのリンク。共有文はJS内の定義済みテンプレートから生成し、**結果の要約はホワイトリスト検証済みIDから引いたラベルのみで構成**する。本文・共有URL・ハッシュタグはすべて `text=` に入れて改行の位置まで固定する（`url=` は本文の末尾に半角スペースで連結されるため、ハッシュタグとリンクが同じ行に並んでしまう）。例:

   ```
   【ルート大全で診断】
   英語:MARCHレベル目標のルートが出ました

   {URL}

   #ルート大全 #大学受験
   ```

   文字数は全角換算でX上限に収まることをテンプレート設計時に確認する(URLは23字換算)。
3. **端末の共有メニュー**: `navigator.share` が使える環境(主にスマホ)ではWeb Share APIボタンを優先表示。非対応環境では非表示にし、1と2のみ出す。
4. 共有ブロック全体はJS初期化成功後にのみ挿入(プログレッシブエンハンスメント)。
5. デザインは既存のボタン・配色のクラスを再利用し、新規CSSは最小限にする。

### 受け入れ条件

- [ ] iOS Safari / Android Chrome / PC Chrome / PC Firefox / PC Safari で3種のボタンが仕様どおり動作(Web Share非対応環境では非表示)
- [ ] コピーされたURLをシークレットウィンドウで開いて同じ結果が再現される
- [ ] X共有画面で文面・URLが正しくプリセットされる
- [ ] 共有文にユーザー入力由来の生文字列が含まれない

## 6. Phase 4: ローカル保存(マイルート)

### タスク

1. 結果画面に「この結果を保存」ボタンを追加。押下で localStorage に保存する。
2. ストレージ設計:

   ```json
   キー: "rt_saved_routes"
   値: {
     "schemaVersion": 1,
     "items": [
       {
         "id": "ランダム生成ID",
         "savedAt": "ISO8601",
         "subjectId": "english",
         "answers": [2,1,3,4,2],
         "label": "英語 / MARCH目標"
       }
     ]
   }
   ```

   - **ここでも保存するのは回答であって結果ではない**(1-1と同じ理由)。表示時に再計算する。
   - 保存上限は10件。超過時は最古を削除する前に確認ダイアログを出す。
3. 診断開始画面に「保存したルート」一覧を表示(保存が1件以上ある場合のみ)。各項目から結果を再表示・削除できる。
4. `localStorage` が使えない環境(プライベートブラウズ等で例外が出る場合がある)では、保存ボタン自体を非表示にする。**必ずtry-catchで機能検出**する。
5. 読み込んだJSONは必ず検証する: `schemaVersion` 不一致・パース失敗・型不正の場合は該当データを破棄し、空状態として扱う(壊れたデータでページが白画面になることを防ぐ)。
6. プライバシーポリシーページに「診断結果の保存にlocalStorageを使用する(第三者送信はしない)」旨の追記をTODOとして提案する(文面案を出力し、適用は運営者判断)。

### 受け入れ条件

- [ ] 保存→リロード→一覧から再表示、が全科目で動作する
- [ ] 11件目の保存で上限処理が仕様どおり動く
- [ ] localStorageに手で壊れたJSONを入れてもページが正常動作する
- [ ] プライベートブラウズ(iOS Safari)で例外が出ず、保存ボタンが非表示になる

### スコープ外(実装しない)

- アカウント機能、サーバー側保存、端末間同期。将来の課題とする。

## 7. Phase 5: SEO・OGP・計測

### タスク

1. **canonical**: 診断ページのcanonicalが**パラメータなしの自ページURL**を指していることを確認する(指していなければ静的に追加)。これでパラメータつきURLの重複インデックスを防ぐ。パラメータつきURL専用のnoindexは実装しない(静的サイトではクエリ別のmeta出し分けが困難であり、canonicalで実用上十分)。
2. **OGP**: 共有URLのOGPは診断ページの静的OGP(既存)がそのまま使われることを確認。結果ごとの動的OGP画像はサーバー処理が必要なため**本計画のスコープ外**とし、将来案としてドキュメントに記録するに留める。
3. **計測**(GA4等が導入済みの場合のみ):
   - `share_copy` / `share_x` / `share_native` / `route_save` / `shared_link_open`(復元表示時)のイベントを送信する。
   - 未導入の場合はイベント送信コードを入れず、フックだけコメントで残す。
4. X側のOGPキャッシュ確認: 実装後、Card Validatorに相当する方法で共有プレビューが正しく出ることを確認する。

### 受け入れ条件

- [ ] パラメータつきURLのレンダリング結果でcanonicalがパラメータなしURLを指す
- [ ] X共有時にサイトのOGPカードが表示される
- [ ] (計測導入済みの場合)5イベントがデバッグビューで確認できる

## 8. Phase 6: テスト・QA

### 自動テスト

既存にテスト環境がなければ、依存追加なしで実行できる最小のテストを用意する(Node標準の `node:test` か、ブラウザで開くだけのテストHTML)。対象:

1. encode/decode のラウンドトリップ(全科目 × 境界値: 全部最小インデックス、全部最大インデックス)
2. 不正入力のファズ的検証(最低30ケース: 空文字、負数、小数、質問数±1、巨大数、非ASCII、`v=0`、`v=2`、`v=abc`、パラメータ順序入替、重複パラメータ)
3. localStorage読み込みの破損データ耐性

### 手動QAチェックリスト

- [ ] 既存の診断フロー(共有機能を使わない通常利用)に**一切のリグレッションがない**
- [ ] 共有→シークレットウィンドウで開く→結果一致、を全科目で1回ずつ
- [ ] スマホ実機(iOS/Android各1)でボタン動作・レイアウト崩れなし
- [ ] 300%ズーム・幅320pxでレイアウト崩れなし
- [ ] JSを無効にして診断ページを開いてもエラー表示や白画面にならない
- [ ] Lighthouseのスコア(特にPerformance/SEO)が実装前から悪化していない

### 受け入れ条件

- [ ] 自動テスト全件パス
- [ ] 手動QA全項目チェック済み
- [ ] 上記をもってmainへマージ可能

## 9. リスクと対応方針(要約)

| リスク | 対応 |
|---|---|
| 将来の診断ロジック変更で旧URLが壊れる | 回答ベース+バージョン管理(1-1, 1-2)。質問構成を変える時は必ず`v`を上げる運用ルールをREADMEに明記 |
| URLパラメータ経由のXSS | ホワイトリスト検証+内部定義ラベルのみ表示(1-3) |
| パラメータURLの重複インデックス | canonical確認(Phase 5) |
| localStorage例外・破損 | 機能検出+検証つき読み込み(Phase 4) |
| 共有ボタンがコンバージョン(書籍リンク)導線を阻害 | 共有ブロックは参考書提示の下に配置(Phase 3) |
| 実装が既存機能を壊す | 触るファイルの限定、Phase 0での調査、リグレッションQA(Phase 6) |
