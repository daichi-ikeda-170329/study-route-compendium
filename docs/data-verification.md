# データの確認基準

このサイトのレコードには、性質の違う 2 種類の情報が混ざっている。**混ぜて表示しない**ことが、
この文書と `build/lib/verification.mjs` の目的である。

| 種類 | 何を含むか | 確かめ方 |
|---|---|---|
| 事実 | 正式書名・出版社・ISBN・刊行年・著者・問題数 | 出版社と書誌データベースで確かめられる。出典 URL と確認日を持てる |
| 推定 | 難易度・到達目安・想定学習時間・長所・注意点・向く人・ルート採用理由 | 運営者 1 人が収録全冊との相対で付けた見立て。**出典は存在しない** |

推定は verified にならない。画面でも「ルート大全による推定」と書く。

## 状態

`build/data/verification.json` が持つ状態は 4 つだけ。

| 状態 | 意味 |
|---|---|
| `verified` | 出典 URL と確認日がある。**この 2 つが無いものを verified にしない** |
| `partial` | 一部の項目だけ確かめてある |
| `unverified` | 確かめていない |
| `notApplicable` | その項目を持たないレコード（ルート上の枠など） |

`physicalReview: true` は「人が実物を確認した」という意味で、**現状は 1 件も立てていない**。
API での照合では立てない。運営者が実物を見たときにだけ立てる。

## 一次情報の優先順位

1. 出版社の公式ページ（商品ページ・正誤表・改訂の告知）
2. 書誌データベース（openBD、国立国会図書館サーチ）
3. 大学・試験実施主体の公式発表（入試情報はここだけを根拠にする）

EC サイトのレビュー、個人ブログ、まとめサイトは**事実確認の根拠にしない**。
自動生成された商品説明も採らない。2 つの出典が食い違うときは一次情報（1）を優先し、
食い違いそのものを `mismatch` として記録する。

## `unverified` の扱い

- **推測で埋めない。** 著者が見つからない本は「著者なし」ではなく未登録として扱う。
- 未確認であることを隠さない。書籍ページには常時「この情報の確かめ方」を出す。
- 未確認でも掲載はする。掲載を止めると、受験生が別の不確かな情報源へ行くだけになる。
- ただし**未確認の値を確定情報として出さない**。構造化データには確かめた ISBN だけを出し、
  書誌データベースと食い違う刊行年は出さない。

## 更新の手順

```bash
node build/fetch-verification.mjs      # openBD と照合して build/data/verification.json を作る
node build/report-data-quality.mjs     # docs/data-quality.md に件数を出す
node build/generate-books.mjs          # 書籍ページの表示を作り直す
```

`build/fetch-verification.mjs` は応答を `build/.cache/openbd/` に置く。再実行しても API へ
行かないので、生成の再現性が保てる（キャッシュは git に入れない）。`--offline` でキャッシュ
だけから作り直せる。API が応答しない ISBN は**未確認のまま残す**。
「確認できなかった」と「確認して間違っていた」を混ぜない。

## 確認の優先順位

受験生が実際に踏む順に確かめる。件数は `docs/data-quality.md` に出る。

1. ルートに採用している教材
2. 3 分診断の結果に出る教材
3. 実際の閲覧が多いページ（Search Console のデータが取れる場合）
4. 情報科（市販書が少なく記載の確度が低い）
5. 新課程対応が要確認の教材
6. その他

## 大学の情報

大学・学部・入試方式の情報は書誌情報とは別に扱う。年度・学部・方式・公式 URL・確認日が
そろわないものを確定情報として表示しない。画面では「大学・学部・入試方式によって必要科目は
異なります。出願時は公式募集要項を確認してください」を必ず添える。
