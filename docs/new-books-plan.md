# 新刊の掲載と X 投稿の運用設計

新しく発売された参考書を検知し、サイトに掲載し、X で投稿するまでの仕組み。
サイトに載っていない既刊を随時足す口も、同じ経路に通す。

策定日: 2026-08-28

運用の正本は次の 2 つに分かれる。X アカウント全体の設計は
[x-account-plan.md](x-account-plan.md)、新刊まわりはこのファイル。

## 1. 目的

[x-account-plan.md](x-account-plan.md) が定めた 3 段（認知 → 来訪 → 収益）のうち、
このファイルが担うのは **収録の鮮度** である。

参考書は毎年 3 月と 9 月に集中して出る。新刊が出た直後にサイトへ載り、X で
「もう載っている」と示せることが、既存の受験系アカウントに対する差になる。
逆に、新刊が半年載らないサイトは「更新が止まっている」と読まれる。

## 2. 全体の流れ

```
週次 GitHub Actions → 楽天ブックス書籍検索 API
                    → 新刊候補（docs/new-books/YYYY-Www.md）
                              ↓
              池田さんが掲載する本を選ぶ ← 人間のゲートはここだけ
                              ↓
              build/data/new-books.json に 1 件追記
                              ↓
   node build/apply-new-books.mjs   5 科目の index.html に BOOKS.push を注入
   node build/generate-*.mjs        書籍ページ・一覧・検索索引・sitemap が追随
   node build/apply-count.mjs       冊数表記を実数へ更新
   node build/gen-x-newbook.mjs     F 型（新刊速報）の投稿文を生成
                              ↓
              池田さんが X に投稿
```

## 3. 前提と制約

### 確認済みの事実

| 事項 | 内容 | 確認日 |
|---|---|---|
| 楽天ブックス書籍検索 API のソート | `-releaseDate`（発売日が新しい順）が使える | 2026-08-28 |
| 同 API の日付絞り込み | **発売日で絞り込むパラメータは無い**。新しい順に取り、日付の判定は自前で行う | 2026-08-28 |
| 同 API の件数 | `hits` は 1〜30、`page` は 1〜100 | 2026-08-28 |
| 同 API の認証 | `applicationId` と `accessKey` が**どちらも必須**と記載。`affiliateId` は任意 | 2026-08-28 |
| 同 API の `salesDate` | 文字列で粒度が可変。「2026年」「2026年08月」「2026年08月28日」に加え、上旬・中旬・下旬・頃・以降などの表現が付く | 2026-08-28 |
| 同 API のレート制限 | 数値の明記は無い。短時間に同一 URL へ多数アクセスすると応答しなくなる旨と、429 が返る旨の記載のみ | 2026-08-28 |

出典は [楽天ブックス書籍検索 API のドキュメント](https://webservice.rakuten.co.jp/documentation/books-book-search)。

### そこから導いた決定

**決定 1: 新刊のメタデータのうち、判断が要る項目は空のまま掲載する。**

新刊は池田さんも Claude も現物を読んでいない。`diff`（難易度 10 段階）・`hensachi`・
`pros`・`cons`・`bestFor` は中身を知らないと書けない。ここを推測で埋めると、
README の「推測で著者名を補わない」と同じ種類の捏造になり、既存 1,052 冊との
難易度の物差しも狂う。

書名・出版社・ISBN・刊行年といった検証可能な事実だけを入れ、判断項目は空にする。
その本には `provisional: true` を立て、サイト上で「新刊・評価準備中」と明示する。

**決定 2: 新刊は `ROUTES`（志望校別ルート）に入れない。**

ルート採用は既存書との比較判断であり、現物未読では決められない。図鑑・検索・
書籍ページには出すが、ルートと診断結果には出さない。評価が固まってから手で入れる。

**決定 3: 自動検知の対象は新刊に限る。既刊の未収録は手動で足す。**

楽天の学参ジャンルには小中学・資格・教科書が混ざる。全件と `BOOKS` を突き合わせると
差分の大半がノイズになり、フィルタの調整に終わりがなくなる。自動検知は
「発売日が最近」の本に絞り、既刊の未収録は気づいたときに `new-books.json` へ
直接足す。**同じ経路を通るので、掲載後の処理はまったく同じである。**

**決定 4: 投稿タイプ F（新刊速報）を新設し、月次バッチとは別に随時生成する。**

既存の `gen-x-posts.mjs` は月次で 1 か月分をまとめて作る。新刊をこれに載せると
投稿が最大 1 か月遅れ、速報としての価値が消える。

## 4. 検知 — `build/fetch-new-books.mjs`

楽天ブックス書籍検索 API を、学参系ジャンルを対象に `-releaseDate` で叩く。

### ジャンル ID を固定値で書かない

学参系のジャンル ID はスクリプトに直書きせず、楽天ブックスジャンル検索 API で
解決して `build/data/rakuten-genres.json` に**取得日つきで**記録する。

```bash
node build/fetch-new-books.mjs --genres   # ジャンル階層を引き直して JSON を更新
```

楽天側のジャンル改編でツリーは変わる。取得方法をコードに残しておけば、
変わったときに引き直すだけで済む。

### 発売日の判定

`salesDate` は文字列で粒度が可変なので、専用のパーサ（`parseSalesDate`）を持つ。

| 入力 | 解釈 |
|---|---|
| `2026年08月28日` | 2026-08-28 |
| `2026年08月` | 2026-08-01（月初として扱う） |
| `2026年08月下旬` | 2026-08-01（旬は捨て、月初として扱う） |
| `2026年` | 2026-01-01 |
| パースできないもの | `null`。**候補からは外さず「発売日不明」として残す** |

パースできないものを捨てないのは、捨てると取りこぼしに気づけないからである。

### 突合とノイズ除去

既存書との突合キーは `isbn`（→ `BOOKS[].isbn13`）。`isbn13` を持たない既存書が
あるので、書名の正規化一致（`assets/js/search.js` と同じ正規化）を補助に使う。

大学受験と無関係な本は `build/data/new-books-filter.json` の除外語で弾く。
**弾いた件数を必ずログに出す。** 黙って減らすと、フィルタが効きすぎていることに
気づけない。

### 出力

- `docs/new-books/YYYY-Www.md` — その週の候補一覧
- `docs/new-books/seen.json` — 一度候補に出した ISBN の記録

`seen.json` があることで、掲載しないと決めた本が毎週出続けない。
`docs/x-posts/used.json` と同じ考え方である。

## 5. 承認 — `build/data/new-books.json`

候補から選んだ本を、池田さんがこの JSON に足す。**ここが唯一の人間のゲート。**

```json
{
  "books": [
    { "id": "…", "subject": "english", "name": "…", "official": "…",
      "pub": "…", "isbn13": "…", "year": 2026, "stage": "tango",
      "provisional": true }
  ]
}
```

必須は `id` / `subject` / `name` / `official` / `pub` / `year` / `stage` / `provisional`。

**`stage`（役割）だけは事実ではなく判断だが、これが無いと図鑑のどこにも置けない**ため、
承認時に必ず決める。書名と出版社の紹介文から役割は判断できる（単語帳なのか
問題集なのか）。難易度は判断できないので空のままにする。

評価が固まったら、この JSON から該当エントリを消し、科目 HTML の `BOOKS` 配列本体へ
`provisional` を外した完全なエントリとして手で移す。**JSON に残っている数が
「評価の残作業」そのものになる。**

## 6. 注入 — `build/apply-new-books.mjs`

各科目 `index.html` に置いたマーカー区間の中身を丸ごと書き換える。

```js
/* NEW BOOKS — 自動生成。build/apply-new-books.mjs が書き換える。手で編集しない */
/* /NEW BOOKS */
```

`build/lib/extract.mjs` は `vm` で script を実行して定数を回収するので、
`BOOKS.push()` された分もそのまま拾える。数学の `ADDITIONAL BOOKS` 区画とは
別物として並置し、既存を巻き込まない。

**マーカーが見つからない科目があったらエラーで止める。** 黙って何もしないと
掲載漏れに気づけない。

## 7. 未評価の表示

`provisional === true` を唯一の根拠にする。バッジ文言は「新刊・評価準備中」。

| 画面 | 扱い |
|---|---|
| 科目トップの図鑑（一覧・モーダル） | 出す。難易度・到達目安の欄はバッジに置き換える |
| 生成ページの一覧 `/<科目>/books/` | 出す。カードのバッジのみ |
| 生成ページの書籍ページ | 出す。難易度・強み・注意点・向いている人の節は出さない |
| 検索 | 出す |
| 志望校別ルート | 出さない（`ROUTES` に入れないので自動的に対象外） |
| 3 分診断の結果 | 出さない（同上） |
| おすすめ | 出さない（ルート採用回数で選ぶため自動的に対象外） |
| X の A 型（図鑑カード） | 出さない。難易度と向く人を書けないため |
| X の F 型（新刊速報） | ここでのみ出す |

### 数字を持たない本が壊す場所

`provisional` な本は `diff` を持たない。次の 3 種類の壊れ方があるので、
描画側で必ず分岐する。

1. `${b.diff}` の素の埋め込み → 画面に `undefined` が出る
2. `b.pros.map(...)` / `b.subjects.split(...)` → **TypeError で描画そのものが止まる**
3. `b.diff<=2 ? … : 3` 形の分類 → 比較が全部 false になり、**最難関に分類される**

3 は静かに間違うので最も危ない。科目トップの `bookLv()` が該当する。

## 8. 冊数の追随 — `build/apply-count.mjs`

`index.html` は 13 箇所（title・meta description・og・twitter・JSON-LD・本文・
統計カード）に冊数を持ち、README の収録数テーブルにもある。

`title` や `meta content` 属性の中に HTML コメントは置けないので、プレースホルダ
方式は採れない。代わりに `build/data/count-state.json` に**前回書き込んだ値**を
持ち、それを新値へ置換する。

**置換件数をログに出し、0 件なら終了コード 1 で止める。** 静かに何もしないと、
冊数だけが古いまま残る。

### 画像に焼き込まれた冊数

| 対象 | 扱い |
|---|---|
| `assets/x-header.png` | SVG が正本としてあるので更新できる。月 1 回、README の Chrome ヘッドレス手順で焼き直す |
| `assets/ogp*.png` 6 枚 | **更新手段が無い（下記）。当面は据え置く** |

`assets/ogp*.png` は元になる SVG も生成スクリプトもリポジトリに存在しない。
README は「`build/` 外の生成手順で作り直す」と書いているが、その手順の実体が無い。
`git log` で追うと初期コミットで PNG が直接追加されたきりである。

掲載を回すことが目的であり、OGP の数字が数十冊ずれても表示は壊れない。ここを
必須にすると運用が止まるので、**据え置きを明示的な決定とする。** SVG ソースを
起こし直す作業は、この設計とは別に切り出す。

## 9. F 型（新刊速報）— `build/gen-x-newbook.mjs`

`new-books.json` のうち未投稿のものについて、投稿文を
`docs/x-posts/new/<subject>-<id>.md` に出す。

**未評価なので難易度も向く人も書かない。** 書けるのは書名・出版社・刊行年・
サイトの書籍ページ URL だけである。`utm_campaign=rt_f_new`。

文字数は `gen-x-posts.mjs` が既に `export` している `weightedLen` を再利用して
検算する（全角 2・半角 1・URL は一律 23、上限 280）。

投稿済みの記録は `docs/x-posts/new/posted.json` に持つ。

## 10. 自動化の切り分け

| 工程 | 担当 | 頻度 |
|---|---|---|
| 新刊候補の収集 | `build/fetch-new-books.mjs` | GitHub Actions が週次実行 |
| 掲載する本の選定 | 池田さん | 週 1 回・数分 |
| `BOOKS` への注入と再生成 | `apply-new-books.mjs` + `generate-*.mjs` | 掲載のたび |
| 冊数の更新 | `apply-count.mjs` | 掲載のたび |
| F 型の本文生成 | `gen-x-newbook.mjs` | 掲載のたび |
| X への投稿 | 池田さん | 掲載のたび |
| 画像の焼き直し | 池田さん | 月 1 回（`x-header` のみ） |

Claude のトークンは掲載 1 件あたりゼロである。判断項目を書かない設計にしたことで、
LLM が入る余地そのものを無くしてある。

## 11. 池田さんが行う操作

**初回のみ**

1. [Rakuten Developers](https://webservice.rakuten.co.jp/) でアプリ ID と
   accessKey を無料取得する（`CONFIG.rakutenId` のアフィリエイト ID とは別物）
2. GitHub のリポジトリ設定で Secrets に `RAKUTEN_APP_ID` と
   `RAKUTEN_ACCESS_KEY` を登録する
3. `node build/fetch-new-books.mjs --genres` を一度流し、学参系のジャンル ID を確定する

**毎週（所要 5 分程度）**

4. `docs/new-books/` の当週分を開き、掲載する本を選ぶ
5. `build/data/new-books.json` に足し、`stage` を決める
6. 再生成コマンドを流し、`docs/x-posts/new/` に出た文を X に投稿する

## 13. リスク

| リスク | 対処 |
|---|---|
| 未評価の本が増え続け、評価が追いつかない | `new-books.json` の件数が残作業そのもの。増えすぎたら掲載ペースを落とす |
| 「評価準備中」ばかりの図鑑になり信頼を損なう | 掲載は選んだ本だけにする。候補を全部入れない |
| 楽天のジャンル改編で検知が止まる | ジャンル ID を JSON に取得日つきで持ち、`--genres` で引き直せるようにしてある |
| 注入スクリプトが 5 科目の HTML を壊す | マーカー欠落はエラーで停止。`test/new-books.test.mjs` で往復を検証する |
| 冊数だけが古いまま残る | 置換 0 件を異常として終了コード 1 で止める |
